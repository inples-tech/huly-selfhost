# Сторож очереди (HLY-5)

## Что было

18.09.2026 после перезагрузки хоста `transactor`, `fulltext` и `telegram-bot`
остались без очереди. Контейнеры стартуют вперемешку, redpanda ещё нет, kafkajs
делает пять попыток на `getaddrinfo ENOTFOUND` и **сдаётся навсегда**. Сервис при
этом живёт и выглядит здоровым: порт слушает, healthcheck зелёный, в логе тишина.
telegram-bot так молчал неделями.

## Что уже сделано (коммит d47c4e8, в проде)

Команда запуска шести потребителей обёрнута ожиданием брокера:

```
until (exec 3<>/dev/tcp/redpanda/9092) 2>/dev/null; do echo "ждём redpanda:9092"; sleep 2; done; exec "$0" "$@"
```

`depends_on` эту задачу не решает: при перезапуске по restart-политике демон
поднимает контейнеры без оглядки на порядок compose. Поэтому ждём в команде.

Проверено 20.09.2026 на отдельном стенде той же командой, что стоит в проде:
без брокера процесс ждёт бесконечно и сервис не стартует, с брокером проходит
сразу. Обёртка есть у всех шести потребителей (`transactor`, `fulltext`,
`telegram-bot`, `account`, `workspace`, `aibot`), пропусков нет.

## Зачем всё-таки сторож

Ожидание закрывает причину — старт раньше брокера. Оно не закрывает все пути в то
же состояние: брокер может упасть и подняться уже после того, как потребитель
подключился. А главное, отказ молчит, и узнать о нём можно только специально
проверив.

`queue-watchdog.sh` берёт состояние групп потребителей у брокера через `rpk`,
сверяет с эталоном и пишет в Telegram, если группа пропала или осталась без
потребителей. Эталон учится сам: любая постоянная группа в состоянии `Stable`
запоминается. Временные группы воркспейсов (`workspace-<24 hex>`) законно
появляются и исчезают — они исключены, иначе сторож давал бы шум.

Расписание: через 5 минут после загрузки (самый опасный момент) и далее раз в час.
Сам не чинит: лечение — `docker restart`, и решать это человеку.

## Почему признак берётся у брокера, а не из логов

Две первые версии сторожа искали в логе `ENOTFOUND redpanda` и **дважды дали
ложную тревогу** по `fulltext`. Сервис спотыкается на старте, переподключается и
про это ничего не пишет — строку `consumer connected to queue` он выдаёт не на
каждое подключение. Состояние группы на брокере — это факт, а не то, что сервис
решил залогировать.

Урок общий: проверка, которая регулярно поднимает ложную тревогу, через полгода
перестаёт читаться, и настоящую аварию в ней не заметят.

## Установка

```bash
install -m 700 ops/queue/queue-watchdog.sh /opt/huly-backup/queue-watchdog.sh
install -m 644 ops/queue/huly-queue-watchdog.{service,timer} /etc/systemd/system/
install -m 644 ops/queue/logrotate.huly-queue-watchdog /etc/logrotate.d/huly-queue-watchdog
systemctl daemon-reload && systemctl enable --now huly-queue-watchdog.timer
```

Первый прогон заводит эталон в `/opt/huly-backup/queue-baseline.txt`. Запускать
его надо на заведомо здоровом стеке, иначе в эталон попадёт неполный набор.

## Проверка

```bash
systemctl start huly-queue-watchdog.service
tail -20 /var/log/huly-queue-watchdog.log
docker exec <стек>-redpanda-1 rpk group list
```

Что сторож НЕ проверен ловить вживую: настоящий отвал сервиса. Срабатывание
проверено подстановкой несуществующей группы в эталон — тревога поднимается,
сообщение уходит. Полная проверка — остановить `telegram-bot` на полминуты и
убедиться, что его группа уходит в `Empty`; на боевом стенде это делать
с ведома владельца.

## Чего не хватает до полного закрытия HLY-5

**Настоящая перезагрузка хоста.** Обёртка ожидания развёрнута, но при последнем
старте контейнеров redpanda уже работал — в логах ноль строк «ждём redpanda»,
то есть цикл ни разу не выполнялся в бою. Единственная полная проверка — ребут,
и это простой на несколько минут.
